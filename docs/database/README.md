# 数据库约定

业务数据位于同一 MySQL 数据库。实际结构由[嵌入式迁移](../../internal/store/migrations/mysql)定义；[按领域组织的 SQL](schema/README.md)作为阅读副本，在结构变更时同步维护，不用于升级已有安装。字段语义、状态和具体事务规则由所属代码及测试表达。

## 存储规则

- 业务表使用单数 snake_case，SQL 引用表名使用反引号；HTTP 集合命名独立于表名。
- 采用 InnoDB、utf8mb4 和明确的排序规则；标识符、令牌等需要精确比较的字段使用适当的二进制比较规则。
- 业务实体 ID 使用 `BIGINT UNSIGNED`，经 API 传输为十进制字符串。版本或摘要按其契约处理，不由客户端解析猜测。
- 时间使用 UTC `DATETIME(3)`，连接时区及解析保持一致；业务服务明确更新修改时间、版本和审计，不依赖 `ON UPDATE` 自动写入。
- 状态使用短字符串，不使用数据库 ENUM。保留主键、唯一键、索引、类型和可空性约束，不设置物理外键或 CHECK；引用、状态组合、权限与跨表一致性在服务事务中验证。
- 参数全部绑定，排序及动态片段使用服务端白名单。运行连接关闭多语句执行，迁移连接按工具需要独立配置。
- 基线不创建数据库、不包含默认口令或初始用户；迁移与安装服务分别承担必要模块初始化和安装数据写入。

支持的数据库版本和验证矩阵以[连接校验](../../internal/store/mysql)及[测试工作流](../../.github/workflows/test.yml)为准。扩展版本范围需验证 DDL、查询及事务语义，不能仅比较主版本号。

## 迁移与验证边界

Goose 管理嵌入式迁移和结构版本，不使用 ORM 自动同步。已发布结构变化通过新增迁移处理，不改写已发布迁移或使用 `IF NOT EXISTS` 隐藏不匹配。未发布阶段按明确任务要求调整基线时，由维护者另行对齐开发环境，应用不自动处理旧结构。

修改基线只影响新安装，不会更新已有库；结构版本相同不等于结构兼容。启动核对版本、关键结构和必需数据，异常时停止业务，不自动改表或清库。保留数据的结构调整需先备份、核对差异，再显式处理并验证安装身份。

MySQL DDL 隐式提交，单文件迁移不保证整体回滚，部分执行失败不能盲目重放。维护与备份流程见[部署与恢复](../operations/deployment.md)。

真实安装、查询、并发与事务行为由[MySQL 测试](../../internal/store/mysql)验证，方法见[测试规范](../development/testing.md#mysql-集成测试)。SQL 阅读副本通过审核维护，不加入 CI 或检查脚本。

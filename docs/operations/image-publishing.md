# 镜像发布与保留

## GHCR 镜像发布与保留

开发镜像、Test 和 Release 是三条独立流程，不互相调用或消费产物；只通过公共 action 复用步骤实现。开发镜像保留推送与手动触发，不设定时构建；Test 响应分支推送、PR 与手动触发；Release 响应版本标签推送，手动执行时也必须选择版本标签。

具体行为分别由[开发镜像工作流](../../.github/workflows/docker-dev.yml)、[测试工作流](../../.github/workflows/test.yml)、[发布工作流](../../.github/workflows/release.yml)、[发布配置](../../.goreleaser.yml)及[清理工作流](../../.github/workflows/ghcr-cleanup.yml)定义。触发分支、镜像地址、标签、架构、Action 版本、并发组和保留数量以这些文件为准，不在正文复制。

每条流程的产物与其本次检查对应同一源码状态。开发镜像构建后运行容器版本命令，与本次二进制版本比较，通过后推送同一个本地镜像；它不承诺完整测试矩阵通过。正式发布独立完成前端、Go 和关键 MySQL 检查，之后由 GoReleaser 生成多平台产物。检查范围见[测试与验证](../development/testing.md)。构建、冒烟或推送失败不能触发清理；重新运行构建也不能以提交时间推断标签新旧。

发布和清理共享串行边界，其他写入同一 package 的自动化也需遵循该约束。清理前检查版本、标签和 manifest 依赖，执行前复核清单未变化；无法证明引用完整或请求失败时停止删除。

[清理检查脚本](../../scripts/check-ghcr-cleanup.mjs)和对应测试负责具体判定。启用构建证明、增加架构或修改标签策略时需重新验证依赖识别，不能把无标签镜像一律当作无引用数据。

需要长期保留或通过 digest 部署的产物应有明确保留策略。镜像条目数量不等于完整历史构建数量。实际仓库权限、部署引用和执行记录维护在本机环境配置中。

独立手动清理通过 GitHub Actions 的清理工作流运行，不要求重新构建镜像。先核对目标 package 和保留条件；失败后检查原因，不绕过依赖验证。

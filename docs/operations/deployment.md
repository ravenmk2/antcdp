# 部署、发布与恢复

本文保留通用操作流程和恢复边界。实际目标、凭据、资源清单与部署记录维护在被忽略的本机配置或部署技能中；配置字段、默认值和完整状态以 [CLI](../../cmd/antcdp)、[配置实现](../../internal/platform/config)和[安装模块](../../internal/modules/install)为准。

## 安装与运行

1. 准备获准的专用空 MySQL 数据库、账号和应用持久化目录。确认目标归属，避免混用旧安装配置、主密钥和业务数据。
2. 将数据库、可选沙箱连接和可信公开来源写入 `conf/config.toml`。配置目录及可选 CA 可只读挂载，`data/` 需要可写并持久化。不要从任意请求 Host 或转发头推断可信来源。
3. 首次启动后，从 `data/install-password` 读取安装口令，进入向导创建创始人账号。完成安装后核对应用就绪、持久化和重启行为。存活检查仅证明进程可响应，不等于数据库或业务可用；就绪探针定义查对应实现。

应用只使用已提供的数据库，不安装数据库服务或自动清空已有环境。配置优先级和校验以源码为准；部署配置与业务设置分别管理，秘密不通过命令行参数、普通响应或日志暴露。

前端和迁移随二进制交付，运行容器不包含构建工具链。容器入口、用户和挂载约定以 [Dockerfile](../../Dockerfile)为准；应用数据、数据库和沙箱卷分别持久化。容器替换不能隐式清空数据，不向工作负载挂载宿主管理接口、Docker socket 或平台数据目录。

默认使用官方 OpenSandbox 服务与原生执行、文件 API，不依赖定制 Server、execd 或文件辅助程序。后端能力通过适配器验证；隔离与可选加固遵守官方能力，不把功能验收当作安全策略完整生效的证据。基础能力和云电脑的分层见[架构总览](../architecture/overview.md)。

## 数据库基线与安装边界

结构执行来源是二进制嵌入的迁移，`docs/database/schema/` 只供阅读。修改基线不会自动改变已有库；版本号相同也不能证明结构一致。发现结构不匹配时停止业务，由维护者备份、核对并显式处理，通用规则见[数据库约定](../database/README.md#迁移与验证边界)。

安装涉及本地文件、DDL 和业务事务，不具备跨存储整体回滚。主密钥、安装身份、配置、完成标记与数据库必须保持一致；异常安装不能被当作全新环境重新生成密钥或覆盖数据。

## 维护与恢复

维护前停止服务并独占数据目录，使用目标版本提供的命令：

```text
antcdp serve --config-dir <config-directory> --data-dir <data-directory>
antcdp db migrate --config-dir <config-directory> --data-dir <data-directory>
antcdp setup recover --config-dir <config-directory> --data-dir <data-directory>
```

迁移和中断安装恢复是不同操作。恢复依据安装身份、数据库及本地记录核实可继续的步骤；部分 DDL 已提交时不能盲目重放整份 SQL。恢复命令不是已安装账号的密码找回入口，详细参数查 CLI。

备份覆盖数据库、完整应用数据及密钥，并单独处理沙箱持久卷。回退须恢复匹配的一组备份。重建测试环境必须明确范围，先核对和处理旧沙箱归属再废弃其账本；需要保留的数据先导出，不以全局 prune 或自动清库完成恢复。

实例回收、卷删除、执行结束和文件发布分别核实。未知结果不能成为重新执行外部副作用的依据，资源释放依赖物理完成证据；具体一致性设计见[执行与恢复](../architecture/agent-runtime.md#外部活动与恢复)。

## 发布与交付

默认先按[测试规范](../development/testing.md)完成本机检查与验收，再提交并按任务要求部署指定 commit。环境部署方式由本机配置或显式调用的部署技能决定。

开发镜像、Test、Release 各自验证本次源码并使用本次构建的产物；公共 action 只共享步骤实现。构建、测试、发布和镜像清理由[工作流](../../.github/workflows)、[发布配置](../../.goreleaser.yml)及对应脚本定义，不在文档重复维护触发条件、标签、架构、保留数量或完整矩阵。

镜像发布与清理遵守共享串行边界，清理先核对 manifest 引用与保留条件，执行前复核目标未变；失败或无法证明引用完整时停止删除。构建成功、远程部署成功和业务验收通过分别报告，不互相替代。
